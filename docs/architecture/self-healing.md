# 🔁 自维护与自愈机制规范（Self-Healing）

> 版本：v1.0  
> 关联文档：`system-overview.md` 第 6 章、自监控服务 `edge-monitor`

---

## 1. 设计目标

- **高可用**：单点故障不导致系统停摆，支持 24/7 长时间运行  
- **可观测**：所有自愈动作都有事件日志与指标记录，可追溯  
- **可控可熔断**：自愈有边界，避免“疯狂重启”；支持人工一键禁用  
- **可配置**：策略、阈值全部外置配置（YAML / 数据库），不写死在代码里

---

## 2. 自愈对象与责任边界

- **服务级别**
  - `edge-api`、`edge-daq`、`ai-softsensor`、`ai-ctrl-optimizer`、`license-service`、`edge-monitor`
  - Docker 容器健康状态、/health HTTP 接口、进程状态
- **数据级别**
  - PLC 连接状态、MQTT 连接状态、InfluxDB / PostgreSQL 读写状态
- **AI 级别**
  - 模型加载、推理结果合法性、模型版本切换
- **OTA 级别**
  - 升级任务、镜像拉取、容器切换与回滚

边界原则：

- **edge-monitor 只负责“发现 + 尝试修复 + 上报”**  
- **最终是否继续运行/停机由运维人员和生产工艺负责人共同决策**

## 3. 服务自愈机制

### 3.1 健康检查规范

- 每个服务必须暴露 `GET /health` 接口，返回：

```json
{
  "status": "ok | degraded | fail",
  "service": "edge-api",
  "uptime_seconds": 12345,
  "dependencies": {
    "postgres": "ok",
    "mqtt": "ok",
    "influxdb": "ok"
  }
}
```

- `status` 约定：
  - `ok`：完全健康
  - `degraded`：功能受限（例如：某些外部依赖暂时不可用）
  - `fail`：服务无法正常对外提供业务能力

### 3.2 周期性检查

- 由 `edge-monitor` 统一调度：
  - 周期：默认 **10s**（可配置）
  - 连续 N 次 `fail`（默认 N=3）视为服务故障

### 3.3 重启策略

当服务被判定为故障时：

1. 记录事件到日志与 MQTT 事件主题：`events/system/self_heal`
2. 通过 Docker API / CLI 执行 **单容器重启**（不动其它服务）
3. 重启后再次观察 M 个周期（默认 M=6）：
   - 若恢复为 `ok` 或 `degraded` → 记录“自愈成功”事件
   - 若仍为 `fail` → 标记为 **自愈失败**，停止进一步自动重启，并发出高等级告警

防抖与熔断：

- 任一服务 **1 小时内自动重启次数 > K（默认 K=5）**：
  - 自动进入 **自愈熔断状态**，不再对该服务做自动重启
  - 推送告警至运维（MQTT / 大屏）

## 4. 数据自愈机制

### 4.1 PLC 连接

- 由 `edge-daq` 维护与 PLC 的 Modbus/TCP 连接
- 自愈措施：
  - 读写失败时，按退避策略重试（例如 1s / 2s / 5s / 10s）
  - 超过最大重试次数后：
    - 报告状态至 `edge-monitor`（通过 MQTT 或专用 API）
    - 在大屏上显示 **“PLC 断连”**，并根据降级策略保持 setpoint 不变

### 4.2 MQTT 连接

- 所有 MQTT 客户端（`edge-daq` / `ai-softsensor` / `ai-ctrl-optimizer` / `edge-api`）都必须实现：
  - 断线自动重连
  - 会话恢复（QoS、保留消息视具体配置）
- `edge-monitor` 通过订阅系统主题（如 `$SYS/#` 或自定义监控主题）感知 Broker 状态。

### 4.3 时序与业务数据库

- InfluxDB 不可用时：
  - **关键实时功能不受影响**（软测量、控制）  
  - 历史曲线暂不可用，API 层返回明确错误码与错误信息
- PostgreSQL 不可用时：
  - 点位表、模型版本表、报警规则等配置读取失败  
  - 系统进入 **只读 / 稳态模式**，不再修改配置

数据自愈策略：

- 定期对数据库做 **连通性检测**（简单 `SELECT 1` / 写入测试点）
- 连续 N 次失败后记录事件，尝试重连，若仍失败则标记为 `degraded`

## 5. AI 自愈机制

### 5.1 模型加载与回滚

- 模型目录结构：

```text
models/
  v1.0.0/
  v1.1.0/
  v1.2.0/
```

- 规则：
  - 所有模型必须为 **ONNX 格式**
  - 当前使用版本记录在：
    - 配置文件：`configs/ai-config.yaml`，或  
    - PostgreSQL 表：`ai_models`（推荐）

加载逻辑：

1. 启动或热切换时，加载“当前版本”模型
2. 加载失败 → 尝试回退到“上一稳定版本”
3. 若连续两次加载失败 → 标记服务为 `fail`，停止推理并上报事件

### 5.2 推理结果校验与降级

- 每次推理后必须做结果合法性校验：
  - 含水率范围是否在 \[0, 100\]% 内
  - 与最近几分钟人工标定值偏差是否在可接受区间内
  - 波动是否过于剧烈（根据 `limits.yaml` 中配置）

若不满足校验规则：

- 第一次触发：仅记录告警（`degraded`）
- 连续 N 次触发：
  - 自动切换为 **简单规则模型** / **经验公式**（内置兜底逻辑）
  - 标记 AI 推理状态为 `degraded`，通知大屏显示 “AI 已降级”

## 6. OTA 自愈机制

### 6.1 升级流程关键点

- 所有升级通过 `scripts/ota-update.sh` 或运维 API 触发
- 使用 Docker 镜像进行原子化升级：
  - 先拉取新镜像
  - 起新容器进行健康检查
  - 健康通过后，再替换旧容器

### 6.2 失败检测与回滚

- 升级失败判定条件（任一满足即视为失败）：
  - 新容器在 T 秒内 `/health` 未返回 `ok`
  - `edge-monitor` 在观察窗口内检测到 `fail` / 大量 error 日志
  - 关键链路（PLC → MQTT → AI → API）中断

失败处理：

1. 自动停止新容器，重新启动旧版本容器
2. 记录 **OTA 回滚事件** 到日志与 PostgreSQL
3. 将本次版本标记为 “不可用”，禁止再次自动升级到该版本

## 7. 配置与策略管理

自愈相关配置建议集中在：

```text
configs/
  qos.yaml        # 自愈频率、重试策略、超时时间
  limits.yaml     # 工艺上限/下限、AI 结果约束
  ai-config.yaml  # 模型版本、自愈开关
```

所有配置变更必须：

- 通过统一配置 API 或工具完成  
- 写入 PostgreSQL 中的“配置变更日志”表  
- 支持在线 reload（不需重启服务）

---

## 8. 运维操作手册（摘要）

- **查看当前自愈状态**
  - 在大屏 / 运维工具中查看系统健康与自愈开关
- **暂时关闭某服务的自动重启**
  - 通过配置中心或运维 API，将该服务的自愈开关设为 `false`
- **手动触发自愈动作**
  - 例如：对特定服务进行“手动重启并观察”
- **查看自愈历史**
  - 从 InfluxDB / PostgreSQL 查询近期自愈事件和结果

---

## 9. 与安全与合规的关系

- 所有自愈动作必须有审计记录（谁、何时、因为什么触发）  
- 禁止未经授权的自动更新配置或模型  
- 在安全策略上，自愈不能绕过授权系统（如 `license-service` 失败时，AI 功能必须保持关闭）
