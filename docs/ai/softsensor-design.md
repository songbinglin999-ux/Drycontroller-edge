# 🧠 含水率软测量服务设计（Softsensor Design）

> 版本：v1.0  
> 关联服务：`ai-softsensor`  
> 关联文档：`model-training-guidelines.md`、`model-versioning.md`、`dataset-spec.md`

---

## 1. 设计目标

- 实时估计烘干后含水率，为控制优化与工艺监控提供依据  
- 具备 **低延迟 / 高稳定 / 可降级 / 可回滚** 的工程能力  
- 支持模型在线升级与多版本管理

---

## 2. 服务架构

### 2.1 组件分解

`ai-softsensor` 内部可拆分为：

- **MQTT 订阅模块**：订阅工艺过程数据 topic  
- **特征工程模块**：构建时间窗口与特征向量  
- **ONNX 推理模块**：加载模型并进行推理  
- **结果发布模块**：将估计含水率发布到 MQTT 与 InfluxDB  
- **健康检查模块**：对外暴露 `/health` 接口，并与自愈机制集成

### 2.2 数据流

```text
MQTT（process/raw/#）
   ↓
ai-softsensor
   ↓ 特征构建 + 标准化
ONNX 模型推理
   ↓
MQTT（ai/moisture/estimation）
InfluxDB（ai_moisture）
```

## 3. 配置与模型加载

### 3.1 配置文件

使用 `configs/ai-config.yaml` 管理：

- 当前使用模型版本号  
- 模型文件路径  
- 特征列表及顺序  
- 标准化参数文件路径  
- 自愈相关开关（如是否允许自动回滚）

### 3.2 模型加载流程

1. 读取配置中 `current_version`，定位模型目录（`models/vX.Y.Z/`）  
2. 加载标准化参数与 ONNX 模型  
3. 进行冷启动自检：
   - 使用一小批内置样本进行推理  
   - 校验推理结果是否在合理范围  
4. 若任一步骤失败，记录错误并触发回滚逻辑。

---

## 4. 推理流程与性能要求

### 4.1 推理触发机制

- 基于 **固定频率触发**（如每 1s / 5s 进行一次推理）  
- 或基于 **数据驱动触发**（当关键点位发生显著变化时触发）

### 4.2 性能指标

- 单次推理延迟：\< 200ms（含特征构建）  
- 端到端延迟（从 PLC 采集到含水率结果生成）：\< 500ms  
- CPU 占用：不影响采集与控制主链路

---

## 5. 结果校验与异常处理

### 5.1 合法性检查

每次推理后，需对结果做基本校验：

- 含水率范围：\[0, 100\]%  
- 与最近一段时间平均值的差异是否过大  
- 与人工标定值的偏差是否持续超标

### 5.2 降级策略

- 若短时间内多次出现异常结果：
  - 标记当前模型状态为 `degraded`  
  - 可切换到更简单、保守的备份模型或经验公式  
  - 同时在 MQTT 与大屏上提示 “AI 已降级”

---

## 6. 日志与监控

- 日志内容建议包括：
  - 模型版本、输入特征统计、推理结果、异常信息  
  - 自愈/回滚动作记录
- 指标监控：
  - 推理 QPS / 延迟分布  
  - 异常结果比例  
  - 模型切换/回滚次数

---

## 7. 与其它模块的接口

- 向 `ai-ctrl-optimizer` 提供：
  - 通过 MQTT 发布的实时含水率估计  
  - 可选：提供最近一段时间的趋势或置信度
- 向 `edge-api` 提供：
  - 通过 InfluxDB 存储的历史含水率曲线  
  - 通过系统状态接口报告当前模型版本与健康状态

---

## 8. 未来扩展

- 引入多模型集成（如不同工况/原料对应不同模型）  
- 根据实时数据自动选择最适合当前工况的模型  
- 在不改变整体架构的前提下扩展到其他软测量任务（如能耗预测等）
